Give every skill an **identity**, and save skill preferences against it, so two skills that share a display name stop being one switch. A skill's name is front matter, and Pi's own loader proves two skills can carry it: it keeps one and shadows the rest. Preferences used to be saved by name, which meant a machine-wide skill and a project's own skill of the same name answered to the same entry — turning one off turned the other off, and the panel could not show both at all. **Settings → Skills** now lists each skill it finds as its own row, saying which scope it belongs to (**Global** or **Project**), where it came from and which file it is, and each switch writes only that skill. A row also says which scope's saved answer is in force, so a project's override reads as an override ("Turned on for this project", beside "Turned on on this machine") and the machine's answer is visibly left alone.

Pi keeps one skill per name, and a preference cannot change what its loader did. The panel is honest about it: a skill Pi shadowed is listed as **not in the list Pi is given**, with the reason, even when its switch is on, so a row never claims a skill a session will not load. Turning the loaded skill off is the one case that reaches a shadowed skill — if the reader turned a specific shadowed skill on, that skill takes the name's place in the session's list, says that it is in the list in place of the skill turned off, and the session's own diagnostics record it. Nothing is put into a session that nobody asked for, so the Skills panel and a running session answer from the same rules.

Preferences written before identities existed keep working, and the migration is safe by construction: a saved name that exactly one discovered skill carries is applied to that skill and becomes its entry the next time a switch is saved; a name that two discovered skills carry is preserved **as it is** and applied to **neither**, with a panel notice naming the skills, rather than spreading one reader's switch over every skill of that name; a name that matches nothing is kept and answers for nothing, and the panel says that too. Reading the panel never rewrites a config file, migration is not repeated once entries are identities, and unrelated keys in the same file — `pathAccess`, `uploads`, a plugin's settings — are left exactly as they were. A config that names the same skill in both the on list and the off list, which only a hand edit or a merge can produce, is reported rather than settled silently.

An identity is read off the skill file's own location, not off the project that happens to be selected: a file under the agent directory is machine-wide, and a file under `<root>/.pi/skills` or a `<root>/.agents/skills` folder belongs to `<root>`, so the panel and a session name the same file the same way. In the **no project** view a project's own skill is no longer offered a machine-wide switch it could never honour, and that view reads no project at all — the repository the web process runs in is not a project the reader opened, so its skills are not listed and its skill files are not parsed. Rows also say where a skill came from more truthfully now: a skill from a Pi skill folder is labelled as one, and a skill from a configured path is labelled as that, which the old labels mixed up. And a switch that is saved correctly but cannot take effect yet — Pi loads a same-named skill, the skill's Pi package is turned off, a running session has not reloaded — is now reported as saved, with the reason, instead of as a failed write.
